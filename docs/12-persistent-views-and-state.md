# 12 — Persistent views and state management

A persistent component panel should continue to receive interactions after the bot process restarts. Persistence is not automatic merely because a message remains visible.

## Conditions for a persistent view

For traditional view persistence patterns, the view must have `timeout=None` and interactive children must have stable `custom_id` values. Register the view with the bot during startup using `bot.add_view(...)`. `LayoutView` is supported by current `discord.py`, but verify the exact semantics for the version you deploy.

## Register during setup

```python
class PersistentStatusLayout(discord.ui.LayoutView):
    def __init__(self):
        super().__init__(timeout=None)
        panel = discord.ui.Container()
        panel.add_item(discord.ui.TextDisplay("# Persistent status panel"))
        button = discord.ui.Button(
            label="Ping", style=discord.ButtonStyle.primary,
            custom_id="zorvex:persistent:ping"
        )
        button.callback = self.ping
        panel.add_item(discord.ui.ActionRow(button))
        self.add_item(panel)

    async def ping(self, interaction: discord.Interaction):
        await interaction.response.send_message("The panel is responding.", ephemeral=True)
```

Register the view before handling interactions, typically as part of bot setup:

```python
class MyBot(commands.Bot):
    async def setup_hook(self):
        self.add_view(PersistentStatusLayout())
```

Import `commands` from `discord.ext` and use the same view definition for registration and message creation. Keep `custom_id` strings stable between deployments.

## Persistent does not mean stateless

`timeout=None` keeps the UI active, but it does not save application state. If a panel displays ticket ownership, a queue, premium status, or a user's permissions, store that state in a database or another durable store. Do not rely on Python object attributes to survive a restart.

## Design IDs intentionally

Use IDs with a clear namespace and action, such as `zorvex:ticket:claim:v1`. Keep them short and avoid including secrets or sensitive data. Since custom IDs route requests, do not treat them as authorisation tokens.

## Message-specific state

For multiple panels of the same type, use database records keyed by message ID, guild ID, or a domain entity ID. Look up the authoritative state inside the callback, re-check permissions, apply a transaction or lock when concurrent actions matter, and then edit the message to reflect the result.

## Race conditions

Two moderators may press a Claim button simultaneously. A safe implementation checks the current owner atomically in persistent storage and accepts at most one claimant. Editing the message alone is not a database lock.

## When not to make a view persistent

Temporary confirmations, ephemeral menus, one-off pagination, or short-lived workflows often benefit from normal timeouts. Persistent interfaces create a long-lived maintenance commitment: the handler must remain compatible with the IDs and state generated by prior deployments.
